# C4 model

Reference: [c4model.com](https://c4model.com/) (read 2026-11-21: abstractions, diagrams, notation,
review checklist).

**C4 is a shape library of the editor, not its rules** (owner's call, 2026-11-25). Everything is
a box; C4's elements are four kinds of box ("Add shape", tab "C4") beside the Basic library's
plain box. Any box stands anywhere, holds any other and can be opened. The model has no levels,
no diagram types and no System Context diagram, and never refuses a shape for where it is put.
What follows is what C4 means by its words, for whoever draws C4 with these shapes; the site is
right where this file differs.

## Abstractions

A software system is made of containers, a container of components, a component of code. People
use software systems.

| Abstraction | What it is | Not |
|---|---|---|
| Person | A user, actor, role or persona. | |
| Software System | The highest level: something that delivers value to its users, built and owned by one team. | A product domain, bounded context, team or squad. |
| Container | An application or a data store: something that must be running for the system to work. Web app, mobile app, serverless function, database, blob store, each queue or topic. "Not Docker." | A JAR, DLL, module or library; the message bus as a whole. |
| Component | Related functionality behind a well-defined interface, inside one container. Not deployable on its own. | A package, namespace or folder (typically). |
| Code | Classes, interfaces, functions, tables. | |

**External** marks a person or software system the team does not own. Only those two can be
external.

## Diagrams

| Diagram | Scope | Shows | In the product |
|---|---|---|---|
| System Landscape | An organisation | People and software systems, with no system in focus | Draw it on the Overview |
| System Context (level 1) | One software system | That system, plus the people and software systems directly connected to it | Not a diagram of its own: the Overview shows it for every system at once |
| Container (level 2) | One software system | Its containers, plus people and software systems directly connected to them | The diagram inside a software system |
| Component (level 3) | One container | Its components, plus the other containers of the same system, people and software systems | The diagram inside a container |
| Code (level 4) | One component | Code elements (classes, interfaces, functions, tables); optional, best generated | The "Code" shapes (J46), on any diagram: one per language, saying what the code is in that language's words |
| Dynamic | A feature or use case | Numbered interactions between elements | Planned as flows (J13) |
| Deployment | One environment | Deployment nodes with container instances | Not built |

How the product fills a diagram, whatever the kinds (`syncView`; it only adds, nothing placed moves):

- The Overview gets every box that stands inside no other, and the connections between them.
- The diagram inside a box gets what that box and its parts are connected to, as cards around
  its frame; what the box itself is connected to has a connector to the frame until a connection
  to a part says it more exactly.
- On the diagram inside a box a connection needs one end inside the box (`connectable`): two
  cards outside the frame are connected on a diagram they are on (J49).
- A connection of a part is drawn inside the box it is in, and shows on every diagram above
  between the cards that hold its ends (`liftedConnections`): one line per pair of cards and
  direction, without a label, and none where that diagram has its own connection between the
  two cards already.

The text formats are C4's (Mermaid's C4 diagrams, D2 as the export writes it) and need a level:
the Overview is written as a context diagram, the diagram inside a software system as a
container diagram, inside anything else as a component diagram, with the box as the boundary.

## What every diagram needs

| The site asks for | How the product does it |
|---|---|
| A title with the diagram type and its scope | `viewTitle`: the name of the box the diagram is inside ("Online Shop"); no type, as there are none |
| A key that explains the notation | `CanvasKey.vue`: lists only what is on the diagram |
| Every element: name, type, a short description | The card |
| Every container and component: its technology | The card, as `[Vue 3]` |
| Every relationship: one direction, a label that says what it is for (not just "Uses") | The connector, drawn from source to target |
| Relationships between containers: the technology or protocol | The connector label, as `Sends orders to [HTTPS]` |
| Colours, shapes and line styles are free, but consistent and explained in the key | One colour and icon per kind; dashed and grey means external. Fading (J22) is a temporary focus on one card, not notation, so it is not in the key |

## Rules for changes

- `canShow` in `packages/model/src/diagram/workspace.ts` decides what a diagram may show: any
  object of the model, from any depth, except the object the diagram is inside and what that
  stands inside (J48). `validateWorkspace` uses the same rule. Change the rule there, with a test, never around it.
- Any new notation (a colour, an icon, a line style, a badge) gets an entry in `CanvasKey.vue`.
- Use the site's names in the UI: Person, Software System, Container, Component.
- Journey J20 checks title, key, description, technology and the external mark.

## Open gaps

1. Something added to a System Context diagram or the landscape by `syncView` cannot be taken
   off again: there is no "remove from diagram" yet.
2. Description, technology and external can only be set when an element is added; J4 brought
   renaming only.
3. A relationship label is optional; the site asks for one on every line.
4. "Directly connected" is not enforced: any person or software system can be placed on a
   Container or Component diagram.
5. "Implied relationships" (the site: a relationship of a container also holds for its software
   system) are drawn (J18), one line for all of them and without their labels; the site leaves
   open whether to draw them.
6. Queues and topics have no notation yet (the site: one container per queue or topic, or "via"
   on the relationship).
